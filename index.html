How I approach a problem

Four steps I keep coming back to, from the first conversation to the hand-over. Pick one.

Start with how people actually work

Before any model, I map where information gets lost. In my internships that meant documenting recruitment and sales workflows and finding the gaps.

  • A written map of the current workflow
  • A short list of gaps, ranked by how much they hurt
  • Requirements a developer can build from

Make the data fit for purpose

Cleaning, preprocessing and balancing come before modelling. For the X-ray classifier that meant handling a heavily imbalanced set of 27,000 images.

  • Cleaned and documented data
  • Class balancing where the classes are lopsided
  • Augmentation when data is limited

Measure honestly, then look inside

Transfer learning gives a strong start with limited data. I measure accuracy, then use tools like Grad-CAM to check the model is looking at the right things.

  • A baseline and a clear evaluation
  • Interpretability plots that show what drove a prediction
  • Notes on where the model is likely to fail

Ship something people can use

A model nobody can use doesn’t help anyone. I wrap the work in a Streamlit app or a backend workflow and explain it in plain language so stakeholders can act on it.

  • A working app or workflow, not just a notebook
  • Documentation written for non-technical readers
  • A walkthrough for the people who will use it
